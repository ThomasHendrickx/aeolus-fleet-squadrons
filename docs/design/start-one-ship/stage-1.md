# Start one ship from a template

Issue: [#33](https://github.com/ThomasHendrickx/aeolus-fleet-squadrons/issues/33). Stage 1 proposal for Thomas: purpose, lessons and questions. No detailed design or implementation is approved by this document.

## Purpose

A person starts one ship from a template version, gives it its own name, and gets it crewed with the template's charter, scopes and crew settings, without making a blueprint or getting a flagship. A company's orchestrator can be a ship with a stable name, made from the same versioned template as other ships doing that work.

Thomas, 20 Nov, verbatim: "this one is a true enabler of standardising the ships".

## Lessons to check against

1. **Remove the workaround the person has today.** #33 records that starting one ship currently needs a one-role blueprint, a flagship and a member name containing a random squadron id. The person's chosen ship name is the outcome, not another way of preparing those parts. Source: [#33](https://github.com/ThomasHendrickx/aeolus-fleet-squadrons/issues/33).
2. **Use the complete template version.** Bases are built into a complete template with a recorded chain; forming keeps a snapshot and later file changes do not change existing ships. Starting directly must preserve charter, parameters, scopes, labels and crew settings. Source: [Files in git and Template bases](../../squadrons.md#files-in-git).
3. **Keep the ship distinct from a squadron role.** A hand-off is currently declared by a template and bound by a blueprint. The flagship supplies the charter at check-in. Removing both leaves real questions about hand-offs and how the crew receives its charter. Source: [Ship template](../../squadrons.md#ship-template) and [check-in](../../squadrons.md#check-in), [decision 0017](../../decisions/0017-squadrons-package.md).
4. **A name is a handle, not a new identity guarantee.** Names are unique among active ships, reusable after retirement and renameable; messages keep resolved ship ids. A chosen stable name cannot promise that a later ship inherits earlier messages. Source: [blueprint, Words and Registry invariants](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/blueprint.md).
5. **Keep ownership, permission to ask and ship powers separate.** The person requesting a ship's existence owns it; the fleet sets the template owner. Approved asking-for-a-ship choices distinguish asking rights and approved ship powers. Today's forming scope subset check is not permission to bypass core. Source: [#41 approved experience 8 and technical choices 16 to 19](../asking-for-a-ship/asking-for-a-ship.md), [forming by message](../../squadrons.md#forming-by-a-ship), [decision 0017](../../decisions/0017-squadrons-package.md).
6. **All forming paths consume the same template count.** Every version and forming path counts together by fleet, configured repository and template name. Crew release does not free a count; confirmed retirement or confirmed failed commission does. Source: [#41, Durable requests and the count](../asking-for-a-ship/asking-for-a-ship.md#durable-requests-and-the-count) and [#43 approved lessons and questions 4 to 7](../template-count-changes/template-count-changes.md).
7. **Crewed is not started.** Crew requests need suitable workspaces, the trierarch starts sessions, and firstPrompt is first-start only. Do not report work started merely because a ship was commissioned. Secrets never travel in forming messages. Source: [Crew settings](../../squadrons.md#crew-settings), [forming by message](../../squadrons.md#forming-by-a-ship), [#41 lessons 7 and 8](../asking-for-a-ship/asking-for-a-ship.md).
8. **Verify what will actually be delivered.** The release correction requires publishing the exact candidate walked on staging, rather than rebuilding it. A future walk of this feature must use the candidate being released and demonstrate one ship with its chosen name and actual template charter. This is a release lesson, not evidence that this feature has been walked. Source: [#57](https://github.com/ThomasHendrickx/aeolus-fleet-squadrons/issues/57) and [fix #58](https://github.com/ThomasHendrickx/aeolus-fleet-squadrons/pull/58).

## Questions

1. **Is this the purpose?** Options: (1) start one named ship from a versioned template, without a blueprint or flagship, as written above; (2) keep one-role blueprints and simplify their form. **Pick: 1**, because #33 identifies the blueprint and extra flagship as the workaround, and templates should standardise individual ships too.
2. **What does the person choose?** Options: (1) template version, ship name and values the template still needs, using its crew settings; (2) also choose squadron role and flagship settings. **Pick: 1**, because these are the concrete inputs for one ship. Exact controls, defaults and permitted overrides wait for the experience design.
3. **What if the name is already in use?** Options: (1) explain that it is in use and let the person choose another, without touching the existing ship; (2) choose a suffix automatically; (3) use or replace the existing ship. **Pick: 1**, because the name is deliberate, especially for an orchestrator. A retry of the same accepted start remains the same start, not a second ship.
4. **What about a template that declares hand-offs?** Options: (1) let the person supply each required destination directly, without a blueprint; (2) initially allow only templates with no hand-offs; (3) supply a hidden flagship. **Pick: 1**, because reusable templates should not need copies just to run individually. Binding must not grant reach. Destination choices and charter delivery need a later design; this pick does not define a new selector or protocol.
5. **Who owns the resulting ship?** Options: (1) the person requesting its existence, preserving #41; (2) the template owner. **Pick: 1**, because standardising how a ship acts does not transfer accountability for the ship. This retains an approved decision; it is not a proposal to reopen it. Acting through another ship must preserve the actual person's ownership through the approved core contract.
6. **How does this fit the count and asking-for-a-ship designs?** Options: (1) starting directly is another forming path under the same template count and approved ownership and powers; (2) direct starts get a separate count and permission path. **Pick: 1**, because separate counts would defeat the approved limit. Detailed dependencies must be resolved before implementation; merging this purpose approves no core contract or #41 open proposal.

## Dependency on #43

#33 adds a forming path. #43 determines the confirmed count that this path must obey, including a reduction below existing ships. A direct start must appear among the ships counted and must not create an exception when another version is chosen. #43's purpose and existing approvals stand without #33; its implementation must include #33 once that path exists. #33 can have its purpose approved independently, but cannot ship a count bypass. Both rely on #41's shared template association and durable count claims. Core rights and identity dependencies stay separate design work.
